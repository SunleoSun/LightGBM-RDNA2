# Histogram correctness and experiment history

The gfx1030 feature4 path has a confirmed dispatch-contract bug for H64/H128. `CUDARowData` uses a 2048-float shared-hist budget on gfx1030, so `DivideCUDAFeatureGroups()` can pack roughly 16 H64 or 8 H128 columns into a 1024-bin partition. `CUDAConstructHistogramDenseFeature4Gfx1030Kernel` is hard-coded to four feature slots and only accumulates/writes those slots. The production fix is to dispatch this kernel only when `max_num_column_per_partition() <= 4`, with a matching launch assertion. H64/H128 therefore fall back to the generic HIP histogram while H256 retains the four-column fast path. A 20-tree H256 CPU-vs-ROCm check after the guard passed structural equality with max prediction difference about `1.37e-7`.

This feature4 bug explained the earlier catastrophic H64/H128 results, but it is not the whole strict-correctness story. With feature4 bypassed, generic HIP produces much closer models but still does not satisfy the CPU-exact smoke gate. H128 `regression_l2` matches CPU structurally and to about `1e-7` prediction error through five boosting iterations, then diverges only at the last split of the sixth tree. H64/H128 binary profiles likewise diverge late in the first tree rather than at the root. These generic HIP differences must not be described as the old feature4 corruption.

The benchmark dataset is not currently a plausible source of this mismatch. `run_benchmarks.py` creates each max-bin training `.bin` with the LightGBM 4.7 CPU library, then feeds that exact binary file to the CPU reference, legacy OpenCL GPU, and ROCm CLI. On binary load, the CUDA path builds `CUDAColumnData` from the already-loaded host FeatureGroups/BinMappers, so it is deriving device storage from the same canonical bins rather than rebucketing raw values independently. Legacy OpenCL likewise packs its device data from the same Dataset iterators.

Legacy OpenCL is a strong architectural control. On the same H64 six-tree smoke dataset it matched CPU tree structure and AUC with max prediction difference about `1.05e-6`; on H128 `regression_l2` it matched CPU tree structure with max prediction difference about `2.03e-7`. The ROCm/CUDA learner on the same binary datasets remained structurally divergent. This points away from Dataset/binning and toward CUDA-learner-specific semantics such as best-split, leaf partition/lifecycle, score/objective integration, or their interaction.

Additional isolation experiments did not move the mismatch: forcing CPU objective routing while retaining the CUDA/HIP tree learner, forcing histogram grid-y to one workgroup, and changing CUDA numerical split counts to prefix-sum per-bin rounded counts all produced essentially the same failing smoke structure. Those experiments were reverted. The August 9 synchronization and geometry rollbacks also remained neutral.

A separate source-confirmed CUDA binary-objective bug existed before the RDNA2 optimization commits. `GetGradientsKernel_BinaryLogloss` converted negative labels to `-1` and then used that value to index the two-element `cuda_label_weights` array. The correct index is the binary class selector `is_pos` (`0` or `1`); `-1/+1` is only the logistic-response sign. The fix applies to both weighted and unweighted-sample branches. It is particularly important for `scale_pos_weight`; the catastrophic weighted-class behavior became a normal close-but-not-strict generic HIP result after this fix.

Accepted performance work from the earlier path remains gfx1030 histogram grid sizing, tuned data-per-thread, reduced CUDA data-partition synchronization, reduced leaf-initialization synchronization, histogram reset queued on the histogram stream, and stream-scoped partition synchronization. These are retained because targeted rollback testing found no correctness effect on H64/H128.

Rejected or neutral experiments include naive concurrent smaller/larger best-split execution because shared state broke correctness; register accumulation that changed floating-point accumulation order and tree structure; direct AMD LDS atomic builtin substitution when it was slower; ordered gradient/Hessian gathers with no speedup; H/G staggering with no clear win; per-grid-y subhistograms with deterministic reduction but no speedup; unsafe atomic/wave compiler flags that regressed performance; MSVC-host plus AMD-clang HIP C++ object mixing that produced incorrect models across the compiler ABI/semantic boundary; CPU-objective-only routing; single-grid-y histogram construction; cumulative-count rewrites in the CUDA best-split kernel; an RDNA2 H64 float-LDS variant that preserved six-tree structure but produced max prediction difference about `1.48e-6` and was slower than the exact double-LDS path; and an H128 two-bank LDS variant that remained exact but showed no meaningful production speedup and was reverted to four banks.

A persistent HIP stream plus ordered async H2D/memset/kernel/D2H and pinned host histogram staging is accepted. It preserves prediction diff `0` and exact CPU structure across smoke and the representative Optuna envelope. H64 improved modestly to roughly `30.7 ms/tree` in a 100-tree production run; H128 was approximately neutral.

Adaptive H64 SuperTile remains accepted as eight features / four double LDS banks / 256 threads, but its threshold has been re-tuned for the mapped-output architecture from 16384 to 12288 rows. Current TIMETAG: 16384 ~756.4 ms kernel / 1.2678 s ConstructHistograms per 100 trees; 12288 ~750.8 ms / 1.2558 s; 10240 ~751.1 ms / 1.2557 s. Because 10240 and 12288 are effectively tied, 12288 is chosen to limit SuperTile use on smaller leaves. A two-bank retest (~28.10 ms/tree) and a 12-feature/three-tuple retest (~28.21) stayed exact but were slower. The final selected shape passes smoke 4/4, feature_fraction 8/8, and representative Optuna 10/10 with prediction diff 0 and exact CPU structure; 100-tree H64 feature_fraction=0.5 measured ~22.88 ms/tree. H128 eight-feature SuperTile remains disabled.

TIMETAG attribution on the measured production profiles found zero Serial histogram fallbacks for both H64 and H128. The observed active counts are profile observations, not backend constants. `ColSampler` randomly samples valid feature indices per tree from the configured fraction and seed, and `RDNA2HistogramEngine` now consumes the canonical `is_feature_used` mask exactly through a canonical group-to-feature map. The dedicated feature-fraction benchmark covers 0.5/0.75/0.9/1.0 and remains CPU/RDNA2 exact after mask-aware LDS/output suppression. Long-run H64/H128 timings improve as the active fraction falls, confirming that disabled atomic work was real overhead.

Rejected exact overlap experiments now include feature-chunk GPU histogram/D2H overlapped with CPU split scanning and disjoint CPU/RDNA2 active-feature ownership. Chunk sizes from 64 to 512 Feature4 tuples all lost to the monolithic path. A stock CPU minority share was especially expensive because `Dataset::ConstructHistograms` gathers ordered gradients/Hessians for the whole indexed leaf; a direct selected-feature dense CPU histogram avoided that gather but still measured roughly `32.1 ms/tree` H64 and `47.9` H128 versus the faster pure-RDNA2 boundary.

Pinning the canonical Serial `DataPartition::indices()` allocation is accepted. It does not change partition ownership or ordering; it only makes leaf-index H2D source pages DMA-friendly. TIMETAG index-copy attribution initially fell by about 47% on both measured profiles, from ~`3.46` to `1.84 ms/tree` H64 and ~`3.76` to `2.02` H128.

Early asynchronous leaf-index preloading is also accepted. RDNA2 overrides the virtual `Split` only to call canonical `SerialTreeLearner::Split` first and then enqueue the already-finalized smaller-leaf index subrange to the device; no split/partition semantics are reimplemented. The next histogram verifies pointer/count identity before consuming the preload and otherwise falls back to the normal copy. TIMETAG observed 2516/2516 H64 and 2589/2589 H128 preload hits, zero fallback copies, and no index-copy time inside `ConstructHistogram`. Smoke, feature_fraction, and Optuna representative suites remained CPU-exact.

Removing the per-dispatch full device histogram memset is accepted. The H64/H128 kernels overwrite all bins of active features with reduced final values, and inactive feature regions are masked out of canonical consumers. The strongest stale-memory check is the scattered feature-fraction suite; all eight fractions/profiles remained prediction-diff `0` and structurally exact, as did smoke and Optuna. TIMETAG removed ~208 ms H64 / ~228 ms H128 of memset work over 100 trees and reduced attributed ConstructHistograms by about 1.56 ms/tree H64 and 2.67 ms/tree H128 in the paired preload-vs-no-memset runs.

Compact Feature4 activity masks are accepted. They are derived every dispatch from the canonical `is_feature_used` vector, so no fixed feature fraction or contiguous layout assumption is introduced. Replacing inner-loop device lookups of group-to-feature mapping and the full feature mask with tuple-local register bit tests kept all correctness gates exact and reduced TIMETAG kernel totals by roughly 9-10% (H64 ~586 -> 534 ms/100 trees; H128 ~725 -> 654).

Mapped canonical histogram output is accepted. Host-registering each exact Serial histogram-pool destination with mapped access and using its HIP device alias for final kernel stores eliminated explicit histogram D2H without changing accumulation precision or order. Smoke, all eight feature-fraction profiles, and the representative Optuna envelope remained prediction-diff `0` and structurally exact. Representative 100-tree production measured ~26.94 ms/tree H64 and ~39.86 H128. TIMETAG moved the PCIe write cost into kernel time (H64 ~758 ms/100 trees, H128 ~1162 ms/100 trees) but removed separate D2H entirely and reduced total ConstructHistograms to ~1.259 s H64 / ~1.678 s H128 over 100 trees. This is a net win despite higher kernel-attributed time.

H128 one-step software prefetch is accepted. The kernel requests next-row index/packed/gradient/Hessian values before the current row's atomics while retaining the same per-thread feature sequence and double accumulation. Smoke, feature_fraction, and all representative Optuna profiles stayed prediction-diff `0` and structurally exact. TIMETAG improved H128 kernel attribution from ~1162 to ~1136 ms/100 trees and ConstructHistograms from ~1.678 to ~1.644 s. Applying the same prefetch to H64 did not show a stable gain and was disabled there.

Compile-time direct/indexed row specialization is accepted. It only replaces runtime pointer selection with template-specialized row access and does not group, reorder, or change arithmetic. Smoke, the complete feature-fraction matrix, and representative Optuna suite remain prediction-diff `0` and structurally exact. TIMETAG H64 improves to ~727 ms kernel / ~1.216 s ConstructHistograms per 100 trees; H128 stays effectively neutral near ~1136 ms / ~1.643 s.

The H64 SuperTile all-active fast path is accepted. It branches once on the existing eight-feature canonical activity mask and, only for `0xff`, removes repeated tuple/group/mask guards while preserving the same row sequence, feature rotation, double LDS atomic sequence, reduction order, and mapped output. TIMETAG improves from ~750.8 to ~745.6 ms kernel and ~1.2558 to ~1.2442 s ConstructHistograms per 100 trees. Smoke 4/4, feature_fraction 8/8, and representative Optuna 10/10 all remain prediction-diff 0 and structurally exact; a 100-tree feature_fraction=1.0 H64 run measured ~26.86 ms/tree.

LDS struct-of-arrays storage is accepted for both exact kernels. Gradient and Hessian planes are separated within each logical LDS histogram bank while all row/feature/double-atomic and bank-reduction ordering remains unchanged. The final accepted H128 refinement adds one padding double between logical H128 banks only; this changes physical LDS placement but not any arithmetic or reduction order. TIMETAG H128 improves further from ~1073.7 to ~1054.7 ms kernel /100 trees and ConstructHistograms from ~1.603 to ~1.572 s; H64 padding was neutral and is not enabled. Smoke 4/4, feature_fraction 8/8, representative Optuna 10/10, and `optuna_long` 8/8 (80,120,200,300,450,650,850,1050 trees) all remain prediction-diff 0 and structurally exact against the pristine upstream v4.7.0 CPU oracle.

Rejected strict-exact micro-probes after mapped output include `double2` final stores, contiguous-bin output thread remapping, raw-bin-0 atomic/store suppression, H64 bank shifts/hash mappings, removing feature rotation, Feature8 packed SuperTile input, interleaved gradient/Hessian device storage, launch-bounds forcing, vectorized LDS zeroing, and current-architecture H64 8-bank/H128 2-bank retests. They were exact when checked but slower and were reverted.

A constant-Hessian scalar kernel specialization was tested and rejected. It avoided the Hessian array H2D/load on constant-Hessian regression, but the specialized H128 kernel became slower enough that total training regressed; the experiment was fully reverted.

A dedicated H64 GPU best-split break-even experiment is rejected in its simple top-K form. Reusing the H128 device-resident pool plus GPU nomination was exact through all short smoke, feature-fraction, representative Optuna, and 100-tree regression gates. H64 top-2 reached about `22.24 ms/tree` on the representative 100-tree workload but diverged by 650 trees (`pred_diff ~0.405`, structure false); top-3 diverged similarly. Top-4 passed the 650-tree gate with `pred_diff ~2.55e-15` and exact structure but cost about `23.98 ms/tree` on the representative 100-tree workload, essentially tying the accepted canonical-CPU-split H64 baseline near `23.95 ms/tree`. The experiment was fully reverted. Do not re-enable H64 GPU ownership with finite top-K alone; any retry needs provable/exact nomination or a materially different cost model.

A direct H128 pool-subtraction/split-nomination fusion is rejected in its tested in-place form. The prototype generated per-feature smaller/larger candidates while replacing the canonical flat parent-minus-current pool update with feature-wave writes and failed strict correctness immediately. The accepted follow-on keeps that flat pool update untouched and uses a read-only scheduling sidecar only for full-feature H128 pairs: the already-proven pair scan runs on the histogram producer stream after pool completion, its results are handed across by re-recording the existing readiness event, and the consumer skips only the duplicate scan while retaining top-2 reduction/gather and CPU exact refinement. Controlled three-run 100-tree A/B measured `25.274` vs `25.776 ms/tree` (~1.95% faster) at feature_fraction 1.0. The same sidecar at feature_fraction 0.9 was slightly slower (`25.772` vs `25.607`) and is therefore gated off for sampled masks. Final correctness remains exact across smoke 4/4, feature-fraction 8/8, Optuna 10/10, H128 regression 100 trees, 650 trees (`pred_diff 2.22e-16`), and 1050 trees (`pred_diff 0`). A subsequent true parent/current read-only selector kept the flat writer authoritative and computed smaller candidates from `current` plus larger candidates from `parent-current` before subtraction. It was exact through 100 trees but averaged `26.261 ms/tree` versus `25.950` for the accepted sidecar in a three-run same-session A/B, so it was fully reverted. This shape duplicates subtraction arithmetic and still reads both full histograms; do not retry it unchanged.

Do not repeat rejected experiments without a new reason or a materially different ownership boundary. The preferred new boundary is a fork-specific `rdna2` learner that keeps Serial/OpenCL host semantics and specializes only the HIP histogram engine first.
