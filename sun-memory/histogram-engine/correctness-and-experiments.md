# Histogram correctness and experiment history

The gfx1030 feature4 path has a confirmed dispatch-contract bug for H64/H128. `CUDARowData` uses a 2048-float shared-hist budget on gfx1030, so `DivideCUDAFeatureGroups()` can pack roughly 16 H64 or 8 H128 columns into a 1024-bin partition. `CUDAConstructHistogramDenseFeature4Gfx1030Kernel` is hard-coded to four feature slots and only accumulates/writes those slots. The production fix is to dispatch this kernel only when `max_num_column_per_partition() <= 4`, with a matching launch assertion. H64/H128 therefore fall back to the generic HIP histogram while H256 retains the four-column fast path. A 20-tree H256 CPU-vs-ROCm check after the guard passed structural equality with max prediction difference about `1.37e-7`.

This feature4 bug explained the earlier catastrophic H64/H128 results, but it is not the whole strict-correctness story. With feature4 bypassed, generic HIP produces much closer models but still does not satisfy the CPU-exact smoke gate. H128 `regression_l2` matches CPU structurally and to about `1e-7` prediction error through five boosting iterations, then diverges only at the last split of the sixth tree. H64/H128 binary profiles likewise diverge late in the first tree rather than at the root. These generic HIP differences must not be described as the old feature4 corruption; their exact numerical/algorithmic cause remains open.

The August 9 SunAgent synchronization and geometry optimizations were explicitly tested as suspects. Restoring the pre-optimization device-wide synchronization in data partitioning, leaf initialization, and histogram reset produced the same H64/H128 smoke results. Restoring default histogram geometry (`min_grid_dim_y=160`, `NUM_DATA_PER_THREAD=400`) also produced the same correctness results, only slower execution. Therefore commits `302ae844`, `43266790`, `dc436ca3`, `53a4b419`, `bfc5b181`, and `45a59373` are not the observed source of the current generic HIP strict mismatch. Their rollbacks were not retained.

A separate source-confirmed CUDA binary-objective bug existed before the RDNA2 optimization commits. `GetGradientsKernel_BinaryLogloss` converted negative labels to `-1` and then used that value to index the two-element `cuda_label_weights` array. The correct index is the binary class selector `is_pos` (`0` or `1`); `-1/+1` is only the logistic-response sign. The fix applies to both weighted and unweighted-sample branches. It is particularly important for `scale_pos_weight`; the catastrophic weighted-class behavior became a normal close-but-not-strict generic HIP result after this fix.

Accepted performance work from the earlier path remains gfx1030 histogram grid sizing, tuned data-per-thread, reduced CUDA data-partition synchronization, reduced leaf-initialization synchronization, histogram reset queued on the histogram stream, and stream-scoped partition synchronization. These are retained because targeted rollback testing found no correctness effect on H64/H128.

Rejected experiments include naive concurrent smaller/larger best-split execution because shared state broke correctness; register accumulation that changed floating-point accumulation order and tree structure; direct AMD LDS atomic builtin substitution when it was slower; ordered gradient/Hessian gathers with no speedup; H/G staggering with no clear win; per-grid-y subhistograms with deterministic reduction but no speedup; unsafe atomic/wave compiler flags that regressed performance; and MSVC-host plus AMD-clang HIP C++ object mixing that produced incorrect models across the compiler ABI/semantic boundary.

Do not repeat rejected experiments without a new reason or a materially different ownership boundary.
