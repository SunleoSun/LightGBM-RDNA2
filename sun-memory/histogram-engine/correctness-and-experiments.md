# Histogram correctness and experiment history

The gfx1030 feature4 path has a confirmed dispatch-contract bug for H64/H128. `CUDARowData` uses a 2048-float shared-hist budget on gfx1030, so `DivideCUDAFeatureGroups()` can pack roughly 16 H64 or 8 H128 columns into a 1024-bin partition. `CUDAConstructHistogramDenseFeature4Gfx1030Kernel` is hard-coded to four feature slots and only accumulates/writes those slots. The production fix is to dispatch this kernel only when `max_num_column_per_partition() <= 4`, with a matching launch assertion. H64/H128 therefore fall back to the generic HIP histogram while H256 retains the four-column fast path. A 20-tree H256 CPU-vs-ROCm check after the guard passed structural equality with max prediction difference about `1.37e-7`.

This feature4 bug explained the earlier catastrophic H64/H128 results, but it is not the whole strict-correctness story. With feature4 bypassed, generic HIP produces much closer models but still does not satisfy the CPU-exact smoke gate. H128 `regression_l2` matches CPU structurally and to about `1e-7` prediction error through five boosting iterations, then diverges only at the last split of the sixth tree. H64/H128 binary profiles likewise diverge late in the first tree rather than at the root. These generic HIP differences must not be described as the old feature4 corruption.

The benchmark dataset is not currently a plausible source of this mismatch. `run_benchmarks.py` creates each max-bin training `.bin` with the LightGBM 4.7 CPU library, then feeds that exact binary file to the CPU reference, legacy OpenCL GPU, and ROCm CLI. On binary load, the CUDA path builds `CUDAColumnData` from the already-loaded host FeatureGroups/BinMappers, so it is deriving device storage from the same canonical bins rather than rebucketing raw values independently. Legacy OpenCL likewise packs its device data from the same Dataset iterators.

Legacy OpenCL is a strong architectural control. On the same H64 six-tree smoke dataset it matched CPU tree structure and AUC with max prediction difference about `1.05e-6`; on H128 `regression_l2` it matched CPU tree structure with max prediction difference about `2.03e-7`. The ROCm/CUDA learner on the same binary datasets remained structurally divergent. This points away from Dataset/binning and toward CUDA-learner-specific semantics such as best-split, leaf partition/lifecycle, score/objective integration, or their interaction.

Additional isolation experiments did not move the mismatch: forcing CPU objective routing while retaining the CUDA/HIP tree learner, forcing histogram grid-y to one workgroup, and changing CUDA numerical split counts to prefix-sum per-bin rounded counts all produced essentially the same failing smoke structure. Those experiments were reverted. The August 9 synchronization and geometry rollbacks also remained neutral.

A separate source-confirmed CUDA binary-objective bug existed before the RDNA2 optimization commits. `GetGradientsKernel_BinaryLogloss` converted negative labels to `-1` and then used that value to index the two-element `cuda_label_weights` array. The correct index is the binary class selector `is_pos` (`0` or `1`); `-1/+1` is only the logistic-response sign. The fix applies to both weighted and unweighted-sample branches. It is particularly important for `scale_pos_weight`; the catastrophic weighted-class behavior became a normal close-but-not-strict generic HIP result after this fix.

Accepted performance work from the earlier path remains gfx1030 histogram grid sizing, tuned data-per-thread, reduced CUDA data-partition synchronization, reduced leaf-initialization synchronization, histogram reset queued on the histogram stream, and stream-scoped partition synchronization. These are retained because targeted rollback testing found no correctness effect on H64/H128.

Rejected or neutral experiments include naive concurrent smaller/larger best-split execution because shared state broke correctness; register accumulation that changed floating-point accumulation order and tree structure; direct AMD LDS atomic builtin substitution when it was slower; ordered gradient/Hessian gathers with no speedup; H/G staggering with no clear win; per-grid-y subhistograms with deterministic reduction but no speedup; unsafe atomic/wave compiler flags that regressed performance; MSVC-host plus AMD-clang HIP C++ object mixing that produced incorrect models across the compiler ABI/semantic boundary; CPU-objective-only routing; single-grid-y histogram construction; cumulative-count rewrites in the CUDA best-split kernel; an RDNA2 H64 float-LDS variant that preserved six-tree structure but produced max prediction difference about `1.48e-6` and was slower than the exact double-LDS path; and an H128 two-bank LDS variant that remained exact but showed no meaningful production speedup and was reverted to four banks.

A persistent HIP stream plus ordered async H2D/memset/kernel/D2H and pinned host histogram staging is accepted. It preserves prediction diff `0` and exact CPU structure across smoke and the representative Optuna envelope. H64 improved modestly to roughly `30.7 ms/tree` in a 100-tree production run; H128 was approximately neutral.

Adaptive H64 SuperTile is accepted for leaves with at least 16384 rows. Eight features / four LDS banks was the best tested geometry and reached about `30.15 ms/tree`; thresholds 8192 and 24576 were slower. H64 12/16-feature tiles and eight banks were slower. H128 eight-feature SuperTile was exact but slower (~`47.6 ms/tree`) and remains disabled.

TIMETAG attribution on the measured production profiles found zero Serial histogram fallbacks for both H64 and H128. The observed active counts are profile observations, not backend constants. `ColSampler` randomly samples valid feature indices per tree from the configured fraction and seed, and `RDNA2HistogramEngine` now consumes the canonical `is_feature_used` mask exactly through a canonical group-to-feature map. The dedicated feature-fraction benchmark covers 0.5/0.75/0.9/1.0 and remains CPU/RDNA2 exact after mask-aware LDS/output suppression. Long-run H64/H128 timings improve as the active fraction falls, confirming that disabled atomic work was real overhead.

Rejected exact overlap experiments now include feature-chunk GPU histogram/D2H overlapped with CPU split scanning and disjoint CPU/RDNA2 active-feature ownership. Chunk sizes from 64 to 512 Feature4 tuples all lost to the monolithic path. A stock CPU minority share was especially expensive because `Dataset::ConstructHistograms` gathers ordered gradients/Hessians for the whole indexed leaf; a direct selected-feature dense CPU histogram avoided that gather but still measured roughly `32.1 ms/tree` H64 and `47.9` H128 versus the faster pure-RDNA2 boundary.

Pinning the canonical Serial `DataPartition::indices()` allocation is accepted. It does not change partition ownership or ordering; it only makes leaf-index H2D source pages DMA-friendly. TIMETAG index-copy attribution initially fell by about 47% on both measured profiles, from ~`3.46` to `1.84 ms/tree` H64 and ~`3.76` to `2.02` H128.

Early asynchronous leaf-index preloading is also accepted. RDNA2 overrides the virtual `Split` only to call canonical `SerialTreeLearner::Split` first and then enqueue the already-finalized smaller-leaf index subrange to the device; no split/partition semantics are reimplemented. The next histogram verifies pointer/count identity before consuming the preload and otherwise falls back to the normal copy. TIMETAG observed 2516/2516 H64 and 2589/2589 H128 preload hits, zero fallback copies, and no index-copy time inside `ConstructHistogram`. Smoke, feature_fraction, and Optuna representative suites remained CPU-exact.

Do not repeat rejected experiments without a new reason or a materially different ownership boundary. The preferred new boundary is a fork-specific `rdna2` learner that keeps Serial/OpenCL host semantics and specializes only the HIP histogram engine first.
