# RX 6800 XT optimization roadmap

The production owner is `device_type=rdna2`: `RDNA2TreeLearner` preserves canonical CPU objective, score, partition, leaf bookkeeping, and fallback split semantics while `RDNA2HistogramEngine` owns gfx1030 data layout/HIP histogram construction. For the exact-safe dense numerical H128 configuration, split nomination is GPU-owned and the two best GPU-nominated features are canonically rescanned on the Ryzen 9 5950X; this now supports arbitrary tree-level `feature_fraction` masks while `feature_fraction_bynode` and unsupported semantics retain the Serial split finder. H64 continues to use the Zen-3 Serial split finder. `device_type=cuda` remains diagnostic; `device_type=gpu` remains legacy OpenCL. CPU LightGBM 4.7 is the correctness oracle.

## Completed foundation

Phase 0 is complete. `device_type=rdna2` is an explicit single-machine backend, uses the canonical CPU-created `Dataset` / `BinMapper`, and does not route through CUDA objective, score updater, best-split finder, or data partition semantics.

The packed dataset foundation is complete for the dense production path. Exact canonical bin IDs are packed once as persistent tuple-major `uint32 feature4[group][row]` storage. For 40k x 3000 this is about 114.44 MiB. The representation is derived from canonical bins and never owns binning semantics.

## Completed H64 and H128 reference kernels

H64 and H128 now have exact HIP histogram producers. Both consume persistent Feature4 data, use 256-thread workgroups and four double-precision LDS banks, support the root and indexed smaller-leaf paths, and write directly into the canonical Serial histogram layout. Gradients/Hessians are uploaded once per tree. Indexed smaller-leaf row IDs are uploaded when needed. Parent-minus-smaller subtraction and best-split evaluation stay on the Serial host path. Cases that require independently constructing both children still use the Serial histogram fallback.

The smoke suite and representative Optuna envelope pass with prediction max diff `0` and exact CPU 4.7 tree structure. The first production 100-tree baselines were about `31.804 ms/tree` H64 versus CPU `49.832`, and `45.525 ms/tree` H128 versus CPU `72.007`.

## Completed transfer/synchronization cleanup

The histogram pipeline now owns one persistent HIP stream. Gradient/Hessian and indexed-leaf H2D copies, histogram memset, kernel launch, and D2H are ordered on that stream. The old device-wide synchronizations around every histogram readback were replaced by one stream synchronization. Histogram D2H targets reusable pinned host staging memory and is then copied into the exact Serial-owned histogram buffer.

This preserves bit-for-bit CPU correctness. Representative 100-tree measurements after the change put H64 around `30.7 ms/tree`, roughly a 3% improvement over the first exact H64 reference. H128 stayed approximately neutral around `46 ms/tree` versus the earlier `45.5 ms/tree` observation, so transfer cleanup is not the main H128 bottleneck. A two-LDS-bank H128 geometry was also neutral and was reverted to four banks.

## Phase 3 - adaptive Feature SuperTile

The H64 SuperTile experiment is now implemented and accepted only as an adaptive large-leaf path. The best tested shape is eight features per 256-thread workgroup (two adjacent Feature4 tuples) with four double-precision LDS banks. Wider H64 tiles were slower: 12 features was about `31.6 ms/tree`, 16 features about `31.4`, and eight features with eight banks about `31.3`. The eight-feature/four-bank path was best, but only for large leaves. A leaf-size threshold of 16384 rows gave the best production result around `30.15 ms/tree`; 8192 was about `30.67` and 24576 regressed to about `31.84`. Smaller leaves therefore remain on the original four-feature kernel.

The first H128 eight-feature SuperTile was exact but slower at about `47.6 ms/tree`, so H128 remains on the four-feature reference kernel. This confirms that row-state reuse must be balanced against LDS occupancy/atomic pressure rather than applied uniformly.

Bottleneck attribution is now measured on 100-tree production profiles with a dedicated `USE_TIMETAG=ON` build. H64: RDNA2 histogram dispatch ~18.66 ms/tree, split scan ~4.31, full tree training ~24.05. Inside histogram dispatch: index H2D ~3.46, memset ~1.74, HIP kernel ~5.12, histogram D2H ~4.18, pinned-staging-to-canonical host memcpy ~4.13. H128: histogram dispatch ~28.33 ms/tree, split scan ~10.28, full tree training ~39.79; index H2D ~3.76, memset ~2.00, kernel ~6.50, D2H ~7.33, host memcpy ~8.72. Gradient/Hessian H2D is only ~0.36-0.39 ms/tree. Production H64/H128 had zero Serial histogram fallbacks. CPU reference split-scan times are nearly the same (~4.65 H64, ~10.84 H128), confirming split semantics are not the reason RDNA2 differs from CPU.

Direct D2H into the canonical Serial histogram is now implemented. `RDNA2HistogramEngine` lazily host-registers each canonical histogram-pool destination, writes the device histogram directly into that pinned buffer, and unregisters all buffers before the base `HistogramPool` is destroyed. If registration fails, the previous pinned-staging path remains as a correctness fallback. TIMETAG confirms `host_copy_ms=0`; production 100-tree results improved to about `28.25 ms/tree` H64 and `41.30 ms/tree` H128 with prediction diff `0` and exact CPU structure.

Canonical active-feature suppression is now implemented. `RDNA2TreeLearner` passes the exact per-dispatch `is_feature_used` vector into `RDNA2HistogramEngine`; the engine maps dense feature groups back to canonical feature indices, uploads the scattered mask, and suppresses both LDS atomics and output writes for disabled features. There is no assumed fraction/count/range. The dedicated `feature_fraction` matrix at 0.5/0.75/0.9/1.0 passes with prediction diff `0` and exact CPU structure. On 100-tree runs, H64 at feature_fraction=0.5 measured about `25.49 ms/tree` versus `28.30` with all features, and H128 at 0.5 about `34.67` versus `42.32` with all features. Full-grid memset/readback remain, so this stage intentionally suppresses feature compute before introducing compact chunk descriptors.

Two CPU/RDNA2 overlap prototypes were tested and rejected in their current form. Feature-chunk histogram/D2H plus CPU split overlap stayed exact but added enough launch, transfer, and OpenMP-region overhead to regress: roughly `65/68 ms/tree` at 64 tuples per chunk, `34/46` at 256 tuples, and `30/44` at 512 tuples for H64/H128, all worse than the monolithic path. Concurrent feature ownership was also exact but slower. The stock CPU histogram constructor paid full ordered-gradient/Hessian gather and OpenMP overhead even for a small CPU feature share; a direct selected-feature CPU histogram avoided that gather but still regressed representative 100-tree runs to roughly `32.1 ms/tree` H64 and `47.9` H128. Do not reintroduce either overlap shape without a materially different batching/ownership mechanism.

The next accepted boundary optimization is pinning canonical `DataPartition::indices()` host storage. `RDNA2HistogramEngine` registers the whole stable index array after Serial initialization and unregisters it before any training-data resize/destruction; indexed smaller-leaf H2D then reads from an already pinned subrange. TIMETAG reduced aggregate index-copy time from roughly `3.46` to `1.84 ms/tree` on H64 and from `3.76` to `2.02 ms/tree` on H128 while preserving exact smoke correctness. Normal wall-clock runs are noisy enough that this micro-optimization should be judged by attributed transfer time rather than a single end-to-end sample.

The first minimal partition-mirror step is now implemented without adopting CUDA partition semantics. After `SerialTreeLearner::Split` finishes and initializes the next smaller leaf, RDNA2 immediately enqueues that leaf's pinned `DataPartition` index subrange into the persistent device index buffer. The next histogram consumes the preloaded device indices on the same stream instead of issuing a critical-path copy. Bagged roots are preloaded after `BeforeTrain`. TIMETAG observed preload hits on all 2516 H64 and 2589 H128 histogram calls, zero fallback copies, and `index_h2d_ms=0` inside `ConstructHistogram`; smoke, feature_fraction, and the full representative Optuna envelope remain prediction-diff `0` with exact CPU structure. This is intentionally still a host-canonical mirror: Serial owns partition order and split decisions.

The full device-histogram memset has now been removed. The accepted H64/H128 kernels overwrite every bin of every active canonical feature with final reduced values (`=` rather than global accumulation), while inactive feature histograms are not consumed by the current Serial split/subtraction path. Therefore zeroing the entire `NumTotalBin * 2` device buffer before every dispatch was redundant. Smoke, the full 0.5/0.75/0.9/1.0 feature-fraction suite, and the representative Optuna envelope all remain prediction-diff `0` with exact CPU structure. TIMETAG confirms `memset_ms=0`; relative to the immediately preceding preload build, aggregate ConstructHistograms time improved from ~16.67 to 15.11 ms/tree H64 and ~21.74 to 19.07 H128. The removed memset itself had cost ~2.08 ms/tree H64 and ~2.28 H128.

Canonical activity metadata is now compacted before the kernel. Instead of uploading the full feature mask and repeatedly reading `group_feature_indices[group]` plus `feature_used[feature]` inside the row/feature inner loop, the host derives one 4-bit activity mask per persistent Feature4 tuple (about 750 bytes for 3000 features). The four-feature kernel loads one tuple mask; the H64 SuperTile combines two masks into one register mask; fully inactive tuples/tiles return before LDS initialization. This keeps the exact scattered `is_feature_used` contract but removes two global lookups from every candidate feature update. TIMETAG kernel totals improved from about 586 to 534 ms over 100 H64 trees and 725 to 654 ms over 100 H128 trees (~9-10%), while smoke, feature_fraction, and the representative Optuna suite remain prediction-diff `0` with exact CPU structure.

Mapped canonical histogram output is now accepted and supersedes explicit histogram D2H on the dense H64/H128 production path. Canonical Serial histogram-pool buffers are host-registered with `Mapped|Portable`; HIP obtains a device alias and the histogram kernels write their final reduced double bins directly into the exact CPU-owned histogram memory. One stream synchronization makes those writes visible before Serial split/subtraction consumers run. If mapping fails, the previous device-histogram -> pinned staging -> host copy path remains as a correctness fallback. This keeps strict CPU-exact `hist_t=double` arithmetic while eliminating bulk histogram DMA entirely. The 100-tree production probes improved to about `26.94 ms/tree` H64 and `39.86 ms/tree` H128 versus CPU `53.96` and `86.84` on the same run; H128 is now very close to the historical OpenCL ~38 ms/tree reference. TIMETAG reports `d2h_ms=0`, `host_copy_ms=0`, `index_h2d_ms=0`, and ConstructHistograms ~12.59 ms/tree H64 / ~16.78 H128. Kernel-attributed time rises because final PCIe host stores are now part of the kernel, but end-to-end histogram time falls substantially. Smoke, feature_fraction, and representative Optuna remain prediction-diff `0` with exact CPU structure.

Safe software prefetch is now accepted for the H128 four-feature kernel only. Each thread loads its next row index, packed Feature4 value, gradient, and Hessian before issuing the current row's LDS atomics, preserving the same per-thread feature order and double accumulation. Applying the same prefetch shape to H64 was performance-neutral/noisy, so H64 keeps the simpler loop while its large leaves continue to use the eight-feature SuperTile. The full smoke, feature_fraction, and representative Optuna envelopes remain prediction-diff `0` with exact CPU structure. Paired mapped-output TIMETAG reduced H128 kernel attribution from ~1162 to ~1136 ms/100 trees and ConstructHistograms from ~1.678 to ~1.644 s; H64 remained essentially neutral (~759 vs ~755 ms kernel). A normal 100-tree H128 probe reached ~38.17 ms/tree in the all-prefetch build, effectively matching the historical OpenCL ~38 reference, though repeated wall-clock runs remain noisy (~39.6 in a later H128-only build).

Direct-row versus indexed-row access is now compile-time specialized in both the four-feature and H64 SuperTile kernels. `USE_INDICES=false` removes the null-pointer selection for direct/full-data leaves; `USE_INDICES=true` removes the reciprocal runtime check for indexed leaves, including H128 prefetch of the next row. Row order, double LDS atomics, mapped output, and Serial ownership are unchanged. Smoke, feature_fraction, and the representative Optuna envelope remain prediction-diff `0` with exact CPU structure. TIMETAG H64 kernel attribution improved from the mapped/prefetch neighborhood of ~755-759 to ~727 ms/100 trees and ConstructHistograms to ~1.216 s; H128 remained essentially neutral at ~1136 ms kernel / ~1.643 s. One normal 100-tree probe measured ~26.20 ms/tree H64 and ~36.50 H128, but the H128 wall-time jump is larger than its unchanged attribution and should be treated as run noise rather than credited to this specialization.

H64 SuperTile threshold/geometry has been re-tuned under mapped canonical output and compile-time direct/indexed row specialization. The accepted geometry remains eight features per workgroup (two Feature4 tuples), four double LDS banks, and 256 threads. The threshold moves from 16384 to 12288 rows. Paired TIMETAG measurements put 16384 at ~756.4 ms kernel / 1.2678 s ConstructHistograms per 100 trees, 12288 at ~750.8 ms / 1.2558 s, and 10240 essentially tied at ~751.1 ms / 1.2557 s; 12288 is preferred because it gets the same attributed benefit while exposing fewer smaller leaves to SuperTile overhead. Wall-clock threshold probes were noisy (roughly 27.3-27.8 ms/tree for the selected shape), so attribution is the selection signal. Re-tested alternatives remained worse: two LDS banks measured ~28.10 ms/tree and a 12-feature/three-tuple SuperTile ~28.21, both exact but slower. Final 100-tree H64 feature_fraction=0.5 measured ~22.88 ms/tree and stayed CPU-exact. Smoke 4/4, feature_fraction 8/8, and representative Optuna 10/10 all pass with prediction diff 0 and exact CPU structure.

The accepted H64 SuperTile now has a uniform all-active fast path. Each eight-feature workgroup already derives one canonical `tile_active_mask`; when all eight bits are set, the kernel skips repeated tuple-boundary, group-boundary, and per-feature mask checks inside the row loop while preserving the exact row order, feature rotation, LDS bank assignment, double atomics, bank reduction, and mapped output. Partial tiles use the original path unchanged. TIMETAG improved H64 kernel attribution from ~750.8 to ~745.6 ms/100 trees and ConstructHistograms from ~1.2558 to ~1.2442 s. A 100-tree feature_fraction=1.0 run measured ~26.86 ms/tree versus CPU ~58.12, and the production feature_fraction=0.9 run measured ~27.21 on that machine load. Smoke 4/4, feature_fraction 8/8, and representative Optuna 10/10 remain prediction-diff 0 with exact CPU structure.

Several strict-exact micro-probes were rejected while profiling the remaining H64 gap: vectorized `double2` mapped stores, remapping output threads for contiguous bins, skipping raw-bin-0 atomics or stores, alternative four-bank lane mappings (`tid>>2`, `tid>>4`, XOR hashing), and removing feature rotation all regressed attributed time. Do not repeat them unchanged.

LDS gradient/Hessian storage is now accepted as struct-of-arrays rather than interleaved pairs. Each logical histogram bank keeps all gradient bins contiguous followed by all Hessian bins, so adjacent bins stride 8 bytes in LDS instead of 16 while the exact same double atomics, row order, bank ownership, and fixed bank-reduction order are preserved. This targets gfx1030 physical LDS-bank conflicts without changing arithmetic. Paired TIMETAG improved H64 kernel attribution from ~745.6 to ~666.4 ms/100 trees (~10.6%) and ConstructHistograms to ~1.153 s; H128 improved from ~1136 to ~1073.7 ms (~5.5%) and ConstructHistograms to ~1.603 s. Production 100-tree runs measured ~25.86 ms/tree H64 versus CPU ~49.52 and ~38.54 H128 versus CPU ~75.29, both prediction-diff 0 with exact CPU structure. Smoke, feature_fraction, and representative Optuna all pass exactly.

The final exact-safe LDS address-layout pass is complete. Feature-stride padding (`NUM_BINS+1`) was neutral/slower and reverted; padding every logical bank was neutral for H64 but improved H128. The accepted final shape therefore adds one double of bank-to-bank LDS padding only in the four-feature H128 kernel (`kEntriesPerBank = 2*kBinsPerBank + 1` for H128), while H64 and the H64 SuperTile retain unpadded SoA. TIMETAG H128 kernel attribution improves from ~1073.7 to ~1054.7 ms/100 trees and ConstructHistograms from ~1.603 to ~1.572 s; H64 remains effectively unchanged. A 100-tree pristine-CPU comparison measured H64 ~25.12 ms/tree versus CPU ~45.71 and H128 ~35.46 versus CPU ~70.32, both prediction-diff 0 and structurally exact. The full smoke 4/4, feature_fraction 8/8, representative Optuna 10/10, and complete `optuna_long` 8/8 horizons through 1050 trees all pass exact.

Kernel micro-tuning is now considered complete for the strict CPU-exact H64/H128 production path. A fresh full-training TIMETAG profile after that closure identifies the next hot boundary: over 100 trees H64 spends about 1.190 s in `ConstructHistograms`, 0.532 s in CPU `FindBestSplitsFromHistograms`, 0.060 s in `SplitInner`, 0.030 s in bagging, 0.018 s in score update, and 0.004 s in binary-objective gradients; H128 spends about 1.594 s in histograms, 1.281 s in CPU best-split scan, 0.065 s in split, 0.028 s in bagging, 0.016 s in score update, and 0.004 s in gradients. Thus best-split evaluation is now the dominant non-histogram training stage, especially H128, while gradients/score/bagging are too small to justify standalone GPU transfers. A Zen-3 host-code A/B using Clang `-march=znver3 -mtune=znver3` preserved exact tree text and reduced TIMETAG best-split scan from ~0.532 to ~0.499 s H64 and ~1.281 to ~1.181 s H128; isolated non-TIMETAG H128 training averaged ~3.03 s versus ~3.10 s generic across four alternating runs, while H64 was neutral at ~1.92 s. The target-specific host flags are therefore accepted for this RX 6800 XT + Ryzen 9 5950X fork. Further unchanged variations of LDS padding, bank count/mapping, feature width, temporal/register aggregation, mapped-output stores, input packing, prefetch, or launch metadata are not justified by measured results.

The accepted H128 best-split architecture is device-resident. In the exact-safe non-TIMETAG production path, the histogram producer no longer writes the full H128 histogram through mapped host memory: it builds into device memory and stores each leaf in a bounded per-leaf device pool. When LightGBM derives the larger child by parent-minus-smaller, RDNA2 forms the larger device histogram from the resident parent and current smaller histogram; the accepted pool update also writes the current smaller slot in the same elementwise kernel, replacing the prior subtract pass plus full device-to-device copy. Best-split selection consumes the resident smaller/larger histograms without bulk histogram H2D/D2H, and device-side reduction returns the top two feature candidates for canonical CPU refinement. The production path is deliberately restricted to the common dense numerical/no-missing H128 case without quantized gradients, categorical/missing semantics, monotone/interaction constraints, by-node feature sampling, extra trees, CEGB/feature penalties, path smoothing, or max-delta clipping; unsupported cases retain Serial ownership. Device-only mode is enabled only when the complete per-leaf pool is allocated, and parent-pool validity is treated as an invariant rather than silently falling back to stale host state.

The selector itself is RDNA2-specific rather than a literal CUDA port. One 256-thread workgroup contains eight native wave32s, one feature per wave; each lane evaluates up to four consecutive right-to-left bins and wave shuffles form the approximate prefix/reduction used only for nomination. A first top-1 prototype matched the CPU winning feature on 5078/5078 leaves in the representative 100-tree shadow but later long-horizon testing exposed rare CPU/GPU FP-order nomination divergence. The accepted production rule is therefore top-2 nomination: the GPU produces the two best feature candidates and the CPU performs canonical `Dataset::FixHistogram` plus `FeatureHistogram::FindBestThreshold` on both before choosing the final `SplitInfo`. GPU arithmetic is never the final semantic owner of the winner.

The non-TIMETAG H128 production path batches the normal smaller/larger leaf pair through one best-split boundary. Both leaves are now scanned in one 2D HIP launch (feature blocks x 2 leaves), then a two-block top-2 reduction directly gathers the selected feature histogram slices into compact device slots. Metadata for both leaves plus all four candidate histogram slots are copied into reusable pinned host buffers before one stream synchronization. This trims pair best-split launch overhead without changing CPU-owned final semantics.

The pair-kernel launch batching is a smaller but repeatable follow-on win after the earlier single-sync readback work. On 100-tree production gates, `feature_fraction=0.9` improved from about `27.685` to `26.984 ms/tree` (~2.5%) and `feature_fraction=1.0` from about `27.179` to `26.586 ms/tree` (~2.2%), both with exact structure. Smoke remains 4/4 exact, feature-fraction remains 8/8 exact, representative Optuna passes, and H128 regression 100 trees passes with prediction diff `1.78e-15`. Long-horizon acceptance also passes: `optuna_d6_balanced_slow` 650 trees measured `18.869 ms/tree` RDNA2 versus `64.999` CPU with prediction diff `2.22e-16` and exact structure, while `optuna_d8_deep_scale64` 1050 trees measured `72.007 ms/tree` RDNA2 versus `141.271` CPU with prediction diff `0` and exact structure.

A cross-stream event handoff is now accepted for the device-only H128 path. `RDNA2HistogramEngine` records a no-timing HIP event after the H128 histogram and per-leaf pool update instead of synchronizing its persistent histogram stream on the CPU. `RDNA2BestSplitEngine` waits for that event on its own persistent stream before launching the pair top-2 scan/reduction/gather. This preserves explicit producer-consumer ordering while collapsing the histogram-side host barrier into the later compact best-split synchronization. ROCm event aliases were added to `cuda_rocm_interop.h` so the existing CUDA-style abstraction remains source-compatible.

The event handoff passes the full correctness envelope: smoke 4/4, feature-fraction 8/8, representative Optuna 10/10, H128 regression 100 trees with prediction diff `1.78e-15`, a 650-tree binary gate with prediction diff `2.22e-16`/exact structure, and a 1050-tree scale-weight gate with prediction diff `0`/exact structure. The follow-on accepted boundary optimization pins the per-dispatch compact Feature4 activity-mask staging buffer. The mask is still rebuilt from canonical `is_feature_used` every dispatch; only its H2D source storage changes from pageable `std::vector` memory to a persistent `cudaHostAlloc`/HIP-pinned buffer. This keeps the async histogram stream from paying repeated pageable-memory staging overhead.

Pinned activity-mask staging gives a material additional H128 gain while preserving semantics. Representative 100-tree H128 measured about `24.097 ms/tree` at `feature_fraction=1.0` versus `26.057` immediately before pinning (~7.5% faster), and about `24.876 ms/tree` at `0.9` versus `26.749` (~7.0% faster). Smoke remains 4/4 exact, feature-fraction 8/8 exact, representative Optuna 10/10 exact, and H128 regression 100 trees passes at about `24.569 ms/tree` with prediction diff `1.78e-15`. Long-horizon acceptance also passes: `optuna_d6_balanced_slow` 650 trees measured `16.867 ms/tree` RDNA2 versus `63.605` CPU with prediction diff `2.22e-16` and exact structure; `optuna_d8_deep_scale64` 1050 trees measured `67.844 ms/tree` RDNA2 versus `142.141` CPU with prediction diff `0` and exact structure.

`FeatureHistogram::is_splittable` remains intentionally conservative in the production GPU-owner path: non-finalized used features are left splittable instead of trusting an approximate GPU negative. A tested GPU-splittable hybrid with CPU rescans of only GPU-negative features was exact but regressed H128 to about `58.5 ms/tree` and was reverted. Top-8 nomination was also correct but unnecessarily expensive; top-2 remains the accepted exactness hedge.

A fresh post-pinning global TIMETAG profile closes the low-hanging host-boundary phase. Under the normal event-overlapped H128 path, TIMETAG wall is about `17.1-17.4 ms/tree` for the representative 100-tree profile, with no Serial histogram fallback, while H64 is about `19.35 ms/tree`. Because event handoff makes histogram submission asynchronous, a temporary TIMETAG-only synchronization was used to isolate GPU stages and then fully reverted. H128 `feature_fraction=0.9` attributes about `8.15 ms/tree` to histogram construction, `6.35 ms/tree` to GPU top-2 best-split scan/reduction/readback, and only `0.73 ms/tree` to canonical CPU refinement; at `feature_fraction=1.0` the corresponding figures are about `7.98`, `6.56`, and `0.91 ms/tree`. H64 remains split between about `11.18 ms/tree` histogram construction and `5.97 ms/tree` canonical CPU best-split scan. Bagging, score update, split bookkeeping, gradient H2D, and partition work are each sub-millisecond per tree and are no longer credible standalone optimization targets.

The apparent sampled-feature best-split `h2d_ms` inflation in the fully overlapped TIMETAG profile was tested by pinning `RDNA2BestSplitEngine::host_used_features_`. That experiment stayed exact but regressed `feature_fraction=0.9` from the accepted ~`24.9 ms/tree` neighborhood to `26.214 ms/tree` and was reverted. The attribution was therefore primarily cross-stream wait placement rather than a profitable pageable-memory staging bottleneck. Do not repeat this pin unchanged. A separate H64 GPU-owner break-even experiment reused the device-resident pool and approximate GPU nomination with canonical CPU refinement. Top-2 was fast on the representative 100-tree H64 profile (~`22.24 ms/tree`) and passed all short smoke/feature-fraction/Optuna gates, but diverged badly by 650 trees (`pred_diff ~0.405`, structure false). Top-3 failed the same 650-tree gate. Top-4 restored exact 650-tree structure (`pred_diff ~2.55e-15`) but measured about `23.98 ms/tree` on the representative 100-tree workload, effectively no better than the accepted CPU-split H64 baseline around `23.95 ms/tree`. Therefore simple H64 GPU top-K ownership does not currently break even under strict correctness and was fully reverted; keep canonical CPU H64 split finding unless nomination becomes provably exact or materially cheaper.

A direct H128 histogram-pool/subtraction + split-nomination fusion was prototyped and rejected in its in-place form. The canonical flat parent-minus-current pool writer remains the sole owner of durable leaf histogram state. A safer follow-on read-only sidecar is now accepted for full-feature (`feature_fraction=1.0`) H128 pair splits: immediately after the canonical pool update, the existing exact-path approximate pair scan is queued on the histogram producer stream against the completed smaller/larger pool, then the histogram-ready event is re-recorded after that scan. The best-split stream waits on the same event and, when the prepared histogram identities match, skips the duplicate pair scan and performs only top-2 reduction/gather, compact D2H, and canonical CPU `FixHistogram`/`FindBestThreshold`. Pool bytes and subtraction ownership are unchanged, and the fallback still runs the original pair scan whenever a prepared sidecar is absent.

The sidecar is intentionally gated to all-feature H128. Same-session three-run A/B on the representative 100-tree workload measured `25.274 ms/tree` sidecar versus `25.776` control at `feature_fraction=1.0` (~1.95% faster). Applying the same scheduling at `feature_fraction=0.9` measured `25.772` versus `25.607` control, so sampled tree-level masks keep the previous best-split path rather than paying sidecar overhead. The final gated build passes smoke 4/4, feature-fraction 8/8, representative Optuna 10/10, H128 regression 100 trees (`pred_diff 1.78e-15`, exact structure), `optuna_d6_balanced_slow` 650 trees (`17.291 ms/tree`, `pred_diff 2.22e-16`, exact structure), and `optuna_d8_deep_scale64` 1050 trees (`pred_diff 0`, exact structure). This is an incremental locality/scheduling win, not the previously hoped-for removal of the ~6.5 ms GPU scan itself.

The remaining plausible double-digit H128 gain still requires reducing scan work or memory traffic rather than merely moving it earlier. A future true parent/current read-only selector may compute larger-child nomination as `parent-current` without writing candidate state into the pool, but it must preserve the flat subtraction kernel as authoritative and reproduce the accepted selector arithmetic exactly before long-horizon validation. CPU micro-tuning cannot recover enough time.

## Later phases

After SuperTile is exact and faster, tune root/no-index specialization, workgroup and bank geometry separately for H64/H128, safe prefetch/temporal aggregation, and constant-Hessian handling. The float-LDS experiment is rejected because it exceeded the strict prediction tolerance and was slower.

Native wave32 equal-bin aggregation comes only after SuperTile is stable. Accumulation-order changes are correctness-sensitive and must pass the full gate.

Dataset construction optimization remains a parallel end-to-end objective: structured timing/peak-RAM measurement, persistent packed caches, fewer host copies, and only later GPU-assisted canonical bin construction if binning itself remains dominant.

H128 best-split ownership now uses device-resident histograms, one 2D smaller/larger feature-scan launch, one two-block top-2 reduction/gather launch, one compact synchronized pair readback, canonical CPU rescans, event-based producer-consumer handoff, and pinned per-dispatch Feature4 activity-mask staging. This is accepted for arbitrary tree-level `feature_fraction` masks under the existing dense numerical/no-missing and no-by-node-sampling constraints, with correctness proven through 1050 trees. Further optimization should be driven by a fresh post-pinning global profile.

## Validation order

1. Focused H64/H128 profile after each kernel change.
2. Full `smoke` suite.
3. Representative `optuna` envelope after a completed optimization.
4. 100-tree production H64/H128 performance comparison only after correctness passes.
5. `optuna_long` before accepting a major architectural stage such as SuperTile/wave32.
6. Keep H256 as a regression check for the separate historical CUDA diagnostic Feature4 path.
