# H64/H128 histogram engine

The production target is RX 6800 XT / gfx1030 on roughly 40k rows by 3000 features. CPU LightGBM 4.7 is the correctness oracle. The device has native wave32 execution and the RDNA2 LDS/bank structure makes aligned/coalesced loads, bank-aware LDS placement, and occupancy/VGPR control important.

The RDNA2 packed-input layer stores exact canonical bins as tuple-major `uint32 feature4[group][row]` in persistent device memory. For 40k x 3000 this is about 114.44 MiB. No OpenCL rebucketing is applied; every byte remains the canonical LightGBM dense-bin ID.

The first production H64 HIP histogram path is implemented. It is enabled only when every feature group is a dense single-feature group and every group has at most 64 bins. One 256-thread workgroup owns each four-feature tuple. The kernel reads aligned packed `uint32` values, uses four LDS histogram banks with lane-dependent feature rotation, accumulates gradient/Hessian pairs in double-precision `hist_t`, reduces the banks, and writes directly into the canonical `GroupBinBoundary` histogram layout expected by `SerialTreeLearner`. Gradients and Hessians are copied to device once per tree; indexed smaller-leaf row IDs are copied as needed. Root and indexed smaller leaves use HIP, while cases that require constructing both children still fall back to Serial construction. Parent-minus-smaller subtraction and CPU split finding remain canonical Serial semantics.

The full smoke and Optuna-envelope suites remain bit-for-bit identical to CPU: prediction max diff `0` and exact tree structure. A 100-tree production-shaped H64 run measured about `31.804 ms/tree` for RDNA2 versus `49.832 ms/tree` for CPU, with identical AUC, predictions, and tree structure. Short smoke timings are dominated by one-time ROCm context/device-allocation and packed-dataset setup and are not representative of amortized training speed.

Double-precision LDS is currently a correctness requirement for the strict gate. A float-LDS variant kept the same six-tree H64 structure but produced max prediction difference about `1.48e-6`, exceeding the project's `1e-6` prediction tolerance, and it was slower in that probe; it was reverted.

Legacy OpenCL `histogram64` remains an architectural/performance reference, not a correctness oracle. Useful ideas include 256 threads, packed four-feature reads, banked LDS, feature rotation, temporal accumulation, prefetch, root specialization, and constant-Hessian handling. The current H64 path intentionally starts simpler while keeping exact CPU semantics.

The first H128 HIP reference is also implemented as a separate compile-time `NUM_BINS=128` instantiation of the same canonical Feature4 producer. It keeps 256 threads and four double-precision LDS banks, requiring about 32 KiB LDS per workgroup versus about 16 KiB for H64, and uses two output rounds because four features times 128 bins exceeds 256 threads. H128 smoke, regression, and the representative Optuna envelope remain prediction-diff `0` with exact CPU structure. A 100-tree production H128 run measured about `45.525 ms/tree` versus CPU `72.007 ms/tree`, with identical AUC, predictions, and structure.

The transfer path now uses one persistent HIP stream: gradients/Hessians and indexed row IDs are queued with async H2D, histogram memset and kernel work are ordered on the same stream, and D2H goes into reusable pinned staging followed by one stream synchronization and a host memcpy into the Serial-owned histogram. This removed per-histogram device-wide synchronization. H64 improved from the first exact reference around `31.8` to about `30.7 ms/tree` in a representative 100-tree run; H128 stayed approximately neutral around `46 ms/tree`. An H128 two-bank LDS trial was neutral and was reverted to four banks.

Adaptive H64 SuperTile is implemented as an eight-feature path: two Feature4 tuples, 256 threads, four double LDS banks, with smaller leaves on the original four-feature kernel. After mapped canonical output and compile-time direct/indexed specialization changed the cost balance, the large-leaf threshold was re-tuned from 16384 to 12288 rows. Current TIMETAG puts 12288 at ~750.8 ms kernel / ~1.2558 s ConstructHistograms per 100 H64 trees versus ~756.4 ms / ~1.2678 s at 16384; 10240 is essentially tied, so 12288 is retained to avoid unnecessarily applying the larger-LDS SuperTile to smaller leaves. Two-bank SuperTile and 12-feature/three-tuple retests were exact but slower (~28.10 and ~28.21 ms/tree respectively). H128 eight-feature SuperTile remains disabled because it was previously exact but slower.

The remaining gap to legacy OpenCL is therefore not simply 'histogram engine missing'. TIMETAG profiling shows the HIP compute kernel is already a minority of total training time: roughly 5.1 ms/tree for H64 and 6.5 ms/tree for H128. The major costs are host/device boundary work and CPU split processing. H64 spends about 8.3 ms/tree on D2H plus host staging memcpy and another 4.3 ms on split scan; H128 spends about 16.1 ms on D2H plus host memcpy and 10.3 ms on split scan. Repeated leaf-index H2D costs another ~3.5-3.8 ms/tree. Serial histogram fallback count is zero on the measured production profiles.

Direct canonical histogram readback is now implemented. Each Serial histogram-pool destination is lazily registered as pinned host memory and becomes the D2H target itself; the old staging buffer remains only as a registration-failure fallback. This removed the measured host histogram memcpy entirely (`host_copy_ms=0`) and improved production 100-tree runs to about `28.25 ms/tree` H64 and `41.30 ms/tree` H128 while preserving exact CPU predictions and tree structure.

The canonical scattered active-feature mask is now consumed inside both the four-feature and H64 SuperTile kernels. Each dense group has an explicit canonical feature-index mapping; disabled features skip LDS atomics and output writes. The 0.5/0.75/0.9/1.0 feature-fraction suite remains bit-for-bit CPU-identical. The mask produces measurable long-run scaling even before compact D2H: H64 0.5 is about `25.49 ms/tree` versus `28.30` at 1.0, and H128 0.5 is about `34.67` versus `42.32` at 1.0.

Naive CPU/RDNA2 overlap at the feature level is not currently a win. Chunked GPU histogram/D2H overlapped with CPU split scanning remained exact but regressed because repeated kernel launches, smaller D2H operations, and OpenMP-region boundaries outweighed overlap. Concurrent disjoint feature ownership also remained exact but slower: the stock CPU constructor pays whole-leaf ordered-gradient/Hessian preparation, while a direct selected-feature CPU implementation removed that gather but still lost to leaving those dense features on RDNA2. Both prototypes were reverted.

The canonical `DataPartition` remains the host owner. Its stable `indices()` allocation is host-registered for HIP, and RDNA2 now takes one additional narrow mirror step: immediately after the canonical Serial split, the next smaller leaf's pinned index subrange is asynchronously preloaded into the persistent device index buffer. The next histogram consumes this already-queued buffer on the same stream. TIMETAG reported 2516/2516 preload hits on H64 and 2589/2589 on H128 with zero critical-path fallback copies and `index_h2d_ms=0` inside histogram construction. Bagged root indices are similarly preloaded after Serial `BeforeTrain`. This gains overlap without duplicating partition rules, boundaries, or child ordering on GPU.

The device histogram is no longer cleared before each dispatch. Both accepted kernels reduce LDS banks and assign final gradient/Hessian values to every bin of every active feature, so a full global memset was not part of the mathematical contract. Inactive feature regions may retain stale device values, but their canonical mask entries prevent their use by split/subtraction consumers. The feature-fraction matrix is therefore the key regression gate. TIMETAG confirms zero memset cost and lower histogram-dispatch time without any correctness change.

Activity checks are now tuple-local rather than feature-global. The host maps the canonical scattered `is_feature_used` vector to one 4-bit byte per Feature4 tuple. Kernels read this compact byte once per workgroup (or combine two bytes for the accepted H64 SuperTile), use register bit tests for feature lanes, and return immediately when an entire tuple/tile is inactive. The device-side group-to-feature map and full feature-used array are no longer needed in the hot path. Paired TIMETAG attribution reduced H64 kernel time from ~586 to ~534 ms/100 trees and H128 from ~725 to ~654 ms/100 trees, with exact CPU output across smoke, feature_fraction, and Optuna.

Final histogram output is now zero-copy from the host consumer's perspective. The canonical Serial histogram buffer is registered as mapped pinned host memory and passed to HIP via `hipHostGetDevicePointer`; after LDS reduction, kernels store final double gradient/Hessian bins directly through that device alias. There is no intermediate device histogram D2H on the mapped path. A stream synchronization remains the ownership boundary before Serial reads the histogram. This preserved strict CPU-exact predictions/structure while dropping production H64 to ~26.94 ms/tree and H128 to ~39.86 in the representative 100-tree run. TIMETAG histogram construction is ~12.59 ms/tree H64 and ~16.78 H128, with explicit D2H/host-copy/index-copy/memset all at zero on the critical path.

The H128 four-feature kernel now uses one-step software prefetch: before current-row atomics, each thread requests the next leaf index / packed tuple / gradient / Hessian into registers. This keeps double arithmetic and per-thread feature order unchanged. The same implementation was not retained for H64 because it did not show a stable benefit; H64 retains the simple loop plus adaptive SuperTile. H128 TIMETAG kernel time dropped from ~1162 to ~1136 ms/100 trees and histogram construction from ~1.678 to ~1.644 s while all strict correctness gates stayed exact.

Both kernel families are additionally specialized at compile time for indexed versus direct rows. This removes `data_indices == nullptr ? ...` from the per-row hot loop while retaining exactly the same row sequence. The H128 prefetch next-row selection is specialized as well. TIMETAG shows a useful H64 reduction to ~727 ms/100 trees and ~1.216 s total histogram construction; H128 remains ~1136 ms / ~1.643 s, so the specialization is mainly an H64 win on the measured production profiles.

The accepted H64 eight-feature SuperTile has a second control-flow specialization for fully active tiles. If its combined canonical activity mask is `0xff`, it omits tuple/group/activity guards inside the row/feature hot loop; otherwise it executes the original guarded path. Arithmetic and ordering are unchanged. After the 12288-row threshold re-tune, this lowers TIMETAG H64 kernel time from ~750.8 to ~745.6 ms/100 trees and ConstructHistograms from ~1.2558 to ~1.2442 s.

The LDS histogram layout is now SoA for both H64 and H128: within each logical histogram bank, all gradient bins are contiguous and the Hessian plane follows. The old interleaved `grad,hess,grad,hess` shape made adjacent bins 16 bytes apart; the SoA shape makes adjacent same-statistic bins 8 bytes apart and reduces gfx1030 physical LDS bank conflicts. No accumulation/reduction ordering changes. TIMETAG improves H64 kernel to ~666.4 ms/100 trees and H128 to ~1073.7 ms/100 trees; 100-tree production measured ~25.86 ms/tree H64 and ~38.54 H128 with exact CPU predictions/structure.

OpenCL itself calls `SerialTreeLearner::FindBestSplits`, but differs in several performance-relevant details: it uses single-precision GPU histogram accumulation by default (`gpu_use_dp=false`), prepares ordered smaller-leaf gradients/Hessians early with pinned buffers, has constant-Hessian specialization, maps histogram output asynchronously, and overlaps GPU dense-histogram work with CPU sparse-feature work. RDNA2 currently prioritizes exact CPU semantics with double-precision LDS.
