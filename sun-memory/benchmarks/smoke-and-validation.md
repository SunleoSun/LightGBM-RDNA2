# Smoke and validation

After an RDNA2 histogram/kernel modification, run the smallest correctness gate first: `python .\benchmarks\windows_rocm\run_matrix.py --suite smoke`. The smoke suite uses `h64`, `h128`, `h64_scale16`, and `h128_regression`, compares the pristine upstream LightGBM v4.7.0 CPU DLL (official commit `8f7036f03627054d5a54a6f965b13f4b9ff2cb63`) against `device_type=rdna2`, trains 6 trees on the full 40k x 3000 training shape, and uses 5000 validation rows. The initial RDNA2 Serial-semantics baseline passes all four with prediction max diff `0` and exact tree text/structure.

Use `--suite optuna` after smoke for the production hyperparameter envelope. It runs 20 trees on ten representative profiles spanning depth `2/3/4/5/6/8`, leaves `4/8/16/32/40/120`, max-bin `63/64/127`, all regularization-profile families, learning rates from `0.085` down to `0.02`, and class-weight extremes together with the smoke scale-16 probe. The current RDNA2 path passes every Optuna profile with prediction max diff `0` and exact tree structure.

Use `--suite feature_fraction` before accepting active-feature compaction or CPU/RDNA2 feature ownership changes. It covers H64/H128 fractions `0.5`, `0.75`, `0.9`, and `1.0` with the canonical feature-fraction seed. LightGBM samples feature indices randomly per tree, so this suite verifies scattered masks rather than a fixed feature prefix. The initial 20-tree run passed all eight profiles with prediction diff `0` and exact CPU structure.

Use `--suite optuna_compat` when a CPU/OpenCL/RDNA2 cross-check is useful. It samples depth 2, depth 4, and depth 8 with `--modes all`. RDNA2 is still gated against LightGBM 4.7 CPU. Legacy OpenCL is reported but not used as the universal correctness oracle because it matched CPU structure at depths 2 and 4 yet diverged at depth 8 / 120 leaves (prediction max diff about `0.00627` and different tree structure). This is evidence that an RDNA2 HIP kernel may borrow the OpenCL architecture without being required to reproduce every OpenCL floating-point split decision.

Use `--suite optuna_long` only at milestone/pre-merge boundaries. It encodes all eight production learning-rate/tree-count pairs: `80@0.085`, `120@0.075`, `200@0.06`, `300@0.05`, `450@0.04`, `650@0.03`, `850@0.025`, and `1050@0.02`. Representative 80-, 120-, 450-, and 1050-tree runs have already passed CPU/RDNA2 exactness. The complete long suite remains intentionally expensive and should be run before accepting a major H64/H128/SuperTile stage rather than after every small kernel edit.

`run_benchmarks.py --modes v470` runs the CPU reference plus `v470_rdna2`. `--modes all` additionally keeps legacy CPU/OpenCL and `v470_cuda_diagnostic`; the CUDA learner is diagnostic only and is not correctness-gated for the RDNA2 path.

If smoke fails, do not use heavier suite results as performance evidence. If smoke passes, `--suite production` provides H64/H128 performance at 100 trees and `--suite stress` provides the older integration matrix at 20 trees (no-bagging, feature_fraction=0.5, scale_pos_weight=16, strong regularization, and regression probes). The Optuna suite complements rather than replaces stress by covering the actual depth/leaf/max-bin/boost envelope.

`python -m pytest tests/c_api_test/rdna2_training_certification.py` adds focused CPU regressions for dense-matrix layout, invalid dimensions, and forced-split boundaries. Use a Python package loading the intended native DLL. `LIGHTGBM_FROZEN_QUANTILE_DIR` points to a Harness export containing `input.json`, `features.f32le`, `labels.f32le`, and the saved CPU `booster.txt`; the CPU test checks the input hashes, exact split structure, and prediction bits. `LIGHTGBM_RUN_RDNA2_CERTIFICATION=1` explicitly enables GPU comparisons on a qualified gfx1030 host; otherwise no test selects Rdna2. Compare identical inputs/configs with CPU as the oracle; inspect both exact split structure and predictions at the usual `1e-6` absolute/relative bounds. This is not a watchdog/stability sign-off. The frozen ETH case also runs with feature bundling and sparse storage disabled to prove the GPU route explicitly: selecting `device_type=rdna2` alone does not guarantee that the raw population or histogram kernels are eligible.

The upstream CPU gate is shape-dependent. After the buffer-lifetime fixes, production-sized smoke (`40,000 × 3,000`, 6 trees) passed 4/4. The compact benchmark (`16,385 × 257`, 20 trees, 2,501 validation rows) passed 25/31. The six failures (H128 binary / deep Optuna profiles) reproduced with identical prediction bits and tree text in the pre-fix and post-fix ROCm DLLs. The compact H128 base case first diverges from CPU at tree 3 (`max_abs_diff=0.036422738680034095`).

On the same pre-fix raw float32 Dataset pipeline, all 18 GPU-built datasets were prediction-bitwise equivalent under the CPU oracle; 16/18 also matched end-to-end. Only H128 quantile alpha=0.9 failed, on both extraction paths (`max_abs_diff=0.10261843659778469`). Holding the training binary fixed, or swapping between the canonical CPU-built and GPU-built versions, reproduces the divergence independently of dataset construction.

The H128 split fix keeps GPU histogram construction but restores Serial ownership of histogram subtraction and per-feature split scanning. The former GPU top-2 path marked unrefined features splittable and reintroduced features that the canonical parent scan had eliminated. On the compact binary profile, the first divergent descendant split in tree 3 used feature 88, which Serial had pruned. The q90 regression similarly reintroduced feature 79 in tree 7. The new compact pytest cases (binary, sampled binary, q90) all fail the tree-structure assertion with the old ROCm library and pass with `max_abs_diff=0` after the fix.

The guarded rerun passed all 44 stages against pristine CPU: 31/31 compact profiles, 18/18 end-to-end Dataset comparisons across nine stages and both extraction modes, and 4/4 production-sized smoke profiles. All compared predictions had `max_abs_diff=0`; dump inventories were unchanged. Serial split ownership has a measurable cost: on production-shaped H128 with 100 trees and 8 threads, median training CLI wall time was 4.905 s versus 2.602 s for the former top-2 path (three alternating runs each). These are local timings on a case where both paths chose the same tree structure, not a reason to restore top-2. The production-shaped long check used 40,000 training rows, 3,000 features, and 5,000 validation rows; each completed profile through 650 trees matched the CPU oracle with `max_abs_diff=0` and exact tree text. The first 850-tree attempt hit the combined CPU/GPU wall-time budget after the CPU oracle completed. Reusing that exact oracle, the separately guarded 850-tree RDNA2 run matched tree text and forecasts (`max_abs_diff=0`). The 1,050-tree class-weight-64 case matched tree text and forecasts on the compact shape (16,385 train rows × 257 features) and on 40,000 × 3,000 with 5,000 holdout rows. On the larger shape the pristine CPU training took 213.53 s, and the RDNA2 CLI training process took 101.16 s, including Dataset load and initialization. No new AMD watchdog or Windows minidumps were detected.

Follow-up H128 performance probes used the same 40,000 × 3,000 binary, 100 trees, alternating trial order, and fixed passive OpenMP waiting. With 8 threads, bulk histogram readback on the full feature mask regressed median CLI wall time from 5.066 to 5.288 s. Building histograms for leaves under 512 rows on Serial also regressed (5.061 → 6.631 s at full feature fraction, 4.933 → 6.293 s at 0.9). Caching the mapped HIP alias also preserved tree text and prediction bits but changed wall time by less than 1% in opposite directions on the two feature masks. All three prototypes were reverted. A separate thread sweep on the mapped baseline measured 6.930 / 4.945 / 4.250 / 4.256 s with 4 / 8 / 16 / 31 threads. All 12 trials had identical tree text and prediction bits. This is a single-profile tuning result, not a change to the library default.

Binary correctness gates include finite/nonconstant probabilities, `[0,1]` range, requested tree count, tight prediction agreement, Pearson correlation, AUC agreement, hard labels at 0.5, confusion matrix, class-balance/tail sanity relative to what the CPU reference itself exhibits, and tree structural signature. Both the minimum predicted-class fraction and confident-tail fraction are capped by the CPU reference value; a two-tree reference that predicts only one hard class must not make an otherwise bit-identical RDNA2 run fail. Regression gates include finite/nonconstant predictions, requested tree count, prediction agreement/correlation, tree structure, and RMSE agreement. Typical binary prediction tolerances are `atol=1e-6`, `rtol=1e-6`, AUC tolerance `5e-8`, and Pearson at least `0.99999999`.
