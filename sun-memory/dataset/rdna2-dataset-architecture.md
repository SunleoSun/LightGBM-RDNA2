# RDNA2 dataset architecture

The RDNA2 backend separates semantic dataset ownership from the physical layout used by HIP kernels. LightGBM `Dataset`, `FeatureGroup`, and `BinMapper` remain the canonical source of feature/bin meaning. RDNA2 must not invent different cut points or rebucket raw values while learner correctness is being established.

The ownership chain is:

`raw input -> canonical LightGBM Dataset/BinMapper -> RDNA2DatasetView -> RDNA2PackedDataset -> RDNA2HistogramEngine`

`RDNA2DatasetView` is the semantic adapter. It exposes canonical feature-to-bin mappings, missing/default-bin semantics, feature-group metadata, row count, max-bin specialization, and the row/column access needed to build the packed representation. It must not redefine bin boundaries.

The first `RDNA2HistogramEngine` dataset layer is implemented and is now the production input for the exact H64/H128 HIP histogram paths. It accepts only gfx1030, enumerates dense single-feature groups, reads their exact canonical bin IDs through `DenseBinIterator`, packs four byte-sized groups into one `uint32`, and uploads tuple-major `[feature4][row]` storage to persistent device memory. It deliberately does not apply legacy OpenCL bin multipliers/random bank offsets because the packed values must remain canonical LightGBM bins. H64/H128 eligibility is detected from canonical per-group bin counts. `RDNA2TreeLearner` constructs this representation during initialization; only unsupported histogram cases fall back to Serial construction.

For the 40k x 3000 production-shaped H64 dataset, the packed device image is about 114.44 MiB (`750 feature4 tuples * 40000 rows * 4 bytes`). A representative gfx1030 probe measured about 25 ms for CPU packing and about 12 ms for the 114 MiB H2D copy after allocation. The first ROCm device allocation/context path cost about 456 ms in that process, which dominates one-time RDNA2 initialization; this cost is distinct from the actual packing and transfer and should not be mistaken for per-tree work. The temporary host packed vector is released when initialization returns; the device representation persists for the learner lifetime.

The packing loop has a production fast path for four ordinary 8-bit dense groups: it reads the four canonical iterators in one row pass and writes one aligned `uint32`, avoiding four read/modify/write passes over the 114 MiB staging buffer. Dense 4-bit groups and incomplete final tuples use a correctness fallback.

Future `RDNA2PackedDataset` work may change the physical representation as long as every packed value maps back to the same canonical bin. The existing aligned `uint32 feature4[group][row]` layout is sufficient for the first SuperTile implementation: a SuperTile can read several adjacent Feature4 tuple bases for the same row without repacking the dataset. H64 and H128 may diverge physically later if profiling proves a dedicated tile layout worthwhile. Repacking per tree or boosting iteration is forbidden.

Histogram readback now targets the Serial-owned canonical histogram buffer directly. `RDNA2HistogramEngine` lazily host-registers each histogram-pool destination and performs async D2H into that pinned memory on the persistent HIP stream, then synchronizes once before CPU consumers run. Registered buffers are unregistered before the base histogram pool is destroyed. Reusable pinned staging remains only as a fallback when host registration fails. This preserves canonical ownership and removes the former staging-to-histogram memcpy.

Dataset construction remains an explicit optimization surface because production observations show it can consume comparable or greater wall time and peak RAM than training. Measure raw parse/load, sampling for bin construction, `BinMapper` construction, canonical bin population, RDNA2 packing, device allocation/context initialization, H2D upload, and training separately. Peak host RAM and device RAM belong in the benchmark contract alongside time.

Optimization order for dataset work is now pipeline-aware:

1. Preserve the causal boundary: every CV fold constructs bin boundaries only from that fold's training rows. The production pipeline uses time-ordered splits with a gap; cross-split Dataset/BinMapper reuse is not an optimization target because later folds contain additional/future rows and reuse can change canonical semantics or create leakage.
2. Remove Python split materialization where the train indices are a contiguous time range. The current `features[train_idx]` shape copies the whole wide matrix; a validated slice/view keeps exactly the same rows and binning authority while eliminating that copy.
3. The first dense C-contiguous float32 `LGBM_DatasetCreateFromMat` rewrite on Ryzen 9 5950X is implemented. The single-matrix/single-machine fast path preserves pristine-v4.7 `BinMapper::FindBin` and generic fallbacks, builds one feature at a time with thread-local double scratch, populates bins directly from float32 without per-row `vector<double>`, and precomputes canonical EFB counts. If every used feature is provably pairwise unbundleable under LightGBM's canonical conflict budget, it reproduces the singleton-group shuffle without materializing per-feature sample-index vectors; sparse/bundleable data falls back to canonical grouping using pre-fixed indices. Next optimize only after profiling the remaining ~1.05-1.15 s construction cost.
4. Separate immutable fold-local binned feature storage from per-model labels/weights where feasible. In production Phase 1, long and short use the same fold feature matrix but currently construct independent Datasets; sharing the fold-local canonical feature bins between the two sides can remove a near-duplicate Dataset build without crossing the fold boundary.
5. Phase 2 may use different long/short selected feature subsets, so any reuse must be a fold-local canonical union/view design rather than blindly sharing a Dataset. Preserve feature-selection semantics and independent labels.
6. Benchmark Optuna throughput, not only single-Dataset latency. The production scheduler can prepare multiple trials while LightGBM Dataset construction itself uses many CPU threads, so Ryzen 5950X thread allocation/concurrency must be tuned to avoid 2-3 simultaneous 31-thread builders oversubscribing 32 hardware threads.
7. Keep existing RDNA2 Feature4 packing/H2D as a secondary surface; current production measurements are tens of milliseconds versus multi-second canonical Dataset construction. Only after CPU construction is reduced should RX 6800 XT take over regular value-to-bin population or direct packed-image generation. GPU acceleration must consume CPU-authoritative bin boundaries and must not require a wasteful GPU->CPU canonical-bin copy followed by CPU repacking.
8. Consider GPU `BinMapper` construction only if profiling after the CPU-memory rewrite proves sorting/boundary construction itself dominant. Any accelerated builder must reproduce canonical sampling, missing/categorical handling, forced bins, `min_data_in_bin`, and feature prefiltering.

The long-term component relationship remains:

`RDNA2TreeLearner(Serial semantics) -> RDNA2HistogramEngine -> RDNA2DatasetView -> RDNA2PackedDataset`

The accepted dense float32 builder materially changes the pre-train profile. On 40k x 3000 with 32 threads and a zero-copy contiguous train view, H64 Dataset construction measured ~1.05-1.06 s versus pristine v4.7 ~2.91-2.98 s, and H128 ~1.09-1.15 s versus pristine ~2.96-3.26 s. Peak working-set growth during candidate construction fell from pristine ~1.54 GiB to ~140-143 MiB. With the production-shaped Python `features[train_idx]` copy still present, H64 candidate construction was ~1.02 s plus ~76 ms split materialization and peak growth was ~599 MiB, of which ~457.8 MiB is the Python split copy; this means the LightGBM optimization alone already removes roughly 1.4 GiB of the former peak, while the later pipeline slice change can remove most of the remainder. The builder scales from ~15.04 s at 1 thread to ~2.12 s at 8, ~1.27 s at 16, and ~1.05 s at 32 on Ryzen 9 5950X, confirming that the former low-utilization construction shape has been replaced by substantial feature-level CPU parallelism. H64 and H128 production serialized binaries are SHA-256 identical to pristine v4.7. Additional byte-identical probes cover dense zeros/NaNs, sparse data that exercises the EFB fallback, categorical features including negative-to-missing handling, and Dataset creation from a reference. 100-tree H64 and H128 end-to-end CPU-vs-RDNA2 gates pass; logical pre-train time is ~1.09 s H64 and ~1.14 s H128, while RDNA2 pack/allocation/H2D remains only ~44-55 ms. A USE_TIMETAG attribution of the accepted dense CPU builder on 40k x 3000 / 32 threads showed H64 Dataset creation at ~1.03-1.06 s: feature-parallel sample/bin work ~0.56-0.57 s, layout ~0.047 s, canonical population ~0.42-0.45 s, FinishLoad negligible. H128 was ~1.14-1.19 s with population ~0.51-0.58 s. Summed CPU time inside the feature-parallel region was dominated by `BinMapper::FindBin` (~14.7-15.1 CPU-s) versus gathering (~2.5-2.9 CPU-s).

The regular population half is now offloaded on the RDNA2 Dataset path. CPU remains the sole owner of sampling and `BinMapper` boundaries. For eligible dense numerical single-feature groups with <=128 bins, a gfx1030 HIP kernel consumes row-major float32 in bounded row chunks, applies the canonical numerical `ValueToBin` rule including NaN semantics, transposes the result to feature-major uint8, and returns each chunk to pinned host memory for direct canonical DenseBin range loading. Unsupported categorical, EFB/multi-feature, sparse, raw-storage, or wider-bin cases fall back to the CPU population path. A process-persistent population context retains its stream, pinned staging, device staging, and boundary metadata buffers; this reduces warm per-Dataset setup to about 1 ms while preserving a one-time ~0.5 s ROCm cold-start cost. On 40k x 3000, warm same-process Dataset creation is ~0.56-0.58 s H64/H128 versus ~0.91-1.04 s for the already optimized CPU builder. The population section itself is ~70-80 ms warm: ~28-31 ms pageable-to-pinned staging, ~30-36 ms H2D+kernel+D2H, and ~10-12 ms canonical host load. H64/H128 serialized binaries are SHA-256 identical to pristine v4.7, targeted zeros/NaNs and fallback cases are byte-identical, and 100-tree end-to-end gates pass. A 500k x 4000 microbenchmark with 8192-row chunks avoids full raw VRAM residency and measured about 0.67 s including host staging for two billion values; chunking was essentially neutral on the 40k x 3000 shape. The next large Dataset owner is therefore CPU `BinMapper::FindBin`, not population, EFB layout, or FinishLoad. The first accepted `FindBin` optimization keeps canonical bin-boundary logic unchanged but replaces the dense-float32 numerical presort only: finite sampled float32 values are stably ordered with a 4-pass IEEE-key radix sort, then widened to double and passed through `FindBinFromSortedValues`; categorical and generic callers retain the original `FindBin` stable-double-sort path. A Ryzen 5950X primitive benchmark over the 40k x 3000 shape measured about 6.07 CPU-s for repeated `stable_sort<double>` versus about 0.55 CPU-s radix-float plus ~0.03 CPU-s float-to-double widening. Full Dataset wall gains are smaller because FindBin post-sort work and memory traffic remain; warm RDNA2 Dataset creation is typically ~0.54-0.60 s H64/H128 after this change. Production H64/H128 serialized Dataset SHA-256 remains identical to pristine v4.7, dedicated zeros/NaNs, sparse-EFB, categorical, and reference probes remain byte-identical, and both 100-tree end-to-end gates pass. A direct `std::sort<double>` replacement was tested separately and rejected because it produced no material wall-time gain. The next accepted step removes the dense numerical float32 widening buffer and the duplicate non-NaN/distinct scan: radix-sorted finite float32 values plus an explicit NaN count now enter `BinMapper::FindBinFromSortedFloat32`, which constructs canonical distinct double values/counts directly and then delegates all bin-boundary, forced-bin, filtering, default-bin, and sparse-rate decisions to the same `FinishFindBinFromDistinctValues` owner used by generic `FindBin`. On 40k x 3000 warm same-process runs this reduced RDNA2 Dataset creation further to about 0.33-0.35 s for both H64/H128; the CPU population variant measured roughly 0.66-0.86 s. Fresh-process RDNA2 construction is about 0.91-0.96 s because the one-time ROCm startup remains. Zero-copy cold peak growth was about 300-305 MiB. H64/H128 production Dataset SHA-256 remains identical to pristine v4.7; zeros/NaNs, sparse-EFB, categorical fallback, and reference probes remain byte-identical, and both 100-tree end-to-end gates pass. Post-radix profiling before this step showed, across two 40k x 3000 builds, summed CPU work of roughly 8-10 s gathering float samples, 4.7-4.9 s radix sorting, 1.3-1.6 s widening, and 13.7-15.0 s post-sort FindBin; eliminating widening and the redundant initial scan therefore removed a real remaining memory/CPU pass without creating a competing binning authority. Dense numerical bin construction also reuses gather/radix workspaces per OpenMP thread instead of allocating them per feature. The next accepted cache-locality step gathers 16 adjacent numerical float32 features in one row-major pass before sorting each feature independently. Sixteen float32 values are exactly one 64-byte cache line, so the production C-row-major matrix is consumed cache-line-wise instead of revisiting one strided feature at a time. Categorical features stay on their canonical separate path. Warm same-process RDNA2 Dataset creation is typically about 0.30-0.35 s H64/H128 on 40k x 3000, while fresh-process construction remains about 0.85-0.90 s because ROCm cold start dominates. Zero-copy cold peak growth remains about 299-306 MiB. Production H64/H128 Dataset binaries remain SHA-256 identical to pristine v4.7, targeted zeros/NaNs, sparse-EFB, categorical, and reference probes remain byte-identical, and both 100-tree end-to-end gates pass. The prior 8-feature block was correct but slightly less favorable in controlled warm measurements; 16 is retained because it matches one 64-byte cache line without increasing observed production peak materially. The first-process RDNA2 cold-start is now partially hidden behind CPU BinMapper construction: only when the persistent population context lacks enough capacity, `LGBM_DatasetCreateFromMats` launches async gfx1030 context/staging preparation while the canonical CPU builder computes boundaries, joins before GPU population, and skips the async path entirely once the context is ready. On fresh 40k x 3000 workers this reduced candidate Dataset creation from the prior ~0.85-0.90 s range to ~0.76-0.78 s H64/H128, with zero-copy peak still ~300-303 MiB. Warm contexts retain the normal synchronous population path and remain around the existing ~0.30-0.37 s load-sensitive range. Production H64/H128 hashes, all targeted special-case hashes, and both 100-tree end-to-end gates remain exact. The overlap is capacity-gated and process-local; it does not change Dataset semantics or make raw data GPU-resident.
